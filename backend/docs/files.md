# Files

Files are notes inside a workspace. Each row in the `files` table holds:

- `id` — UUID generated by Postgres
- `workspace_id` — FK to `workspaces.id`
- `title` — display name (e.g. `notes.txt`)
- `content` — HTML produced by the editor
- `storage_path` — defined in the schema and written by the legacy
  `db.create_file()` helper, but **not** written by `POST /files/save`
  (which uses `content` instead). See [database.md](./database.md).

Every file endpoint requires `Authorization: Bearer <jwt>` and calls
`verify_workspace_ownership()` after looking up the file's workspace.

## `POST /files/save`

Create a new file or update an existing one. Also rebuilds the
`file_links` table for the saved file.

- **Auth:** required + workspace membership.
- **Request body** (`FileSaveRequest`):
  ```json
  {
    "workspace_id": "<uuid>",
    "file_id": "<uuid|temp-...|null>",
    "file_name": "notes.txt",
    "file_contents": "<p>html string</p>",
    "linked_file_names": ["other.txt", "another.txt"]
  }
  ```
- **Behavior:**
  - If `file_id` is present **and** does not start with `temp-`, the
    handler issues an `UPDATE` on `files` keyed by that id. If the update
    returns zero rows it raises `403` with the message about RLS — see
    "Update blocked" below.
  - Otherwise it issues an `INSERT` and uses the new id from the response.
    The `temp-...` placeholder pattern is what the frontend uses for
    files the user has created locally but never saved.
  - After the file row is in place, every row in `file_links` whose
    `source_file_id` equals this file is deleted, and one new row is
    inserted per entry in `linked_file_names`. Links are resolved by
    title within the same workspace; entries that don't match any file
    are silently dropped.
- **200 OK:** `{ "file_id": "<uuid>", "message": "File saved" }`.
- **400 Bad Request:** `{ "detail": "Failed to create file" }` when the
  insert returns no row.
- **403 Forbidden:** `{ "detail": "Update blocked by Supabase. You likely
  need to update your RLS policies to allow shared users to edit
  files." }` when the update returns zero rows. This commonly means RLS
  is rejecting the write; the message is surfaced verbatim from the
  handler.

### Linking and the `[[ ]]` syntax

The frontend (`TextEditor.tsx`) inserts a TipTap link of the form
`<a href="#note:<file-id>">title</a>` whenever the user types `[[` and
picks a file. On save, the editor scrapes those anchors, collects their
text content, and posts it as `linked_file_names`. The backend resolves
each name back to a file id within the same workspace and writes one row
to `file_links`. This is what powers the workspace graph view.

## `GET /files/{file_id}`

Fetch a single file with its content.

- **Auth:** required + workspace membership (resolved via the file's
  `workspace_id`).
- **Path parameter:** `file_id` (UUID).
- **200 OK:**
  ```json
  {
    "file_id": "<uuid>",
    "title": "notes.txt",
    "content": "<p>...</p>",
    "workspace_id": "<uuid>"
  }
  ```
- **404 Not Found:** when the file id does not exist.

## `GET /workspaces/{workspace_id}/files`

List every file in a workspace.

- **Auth:** required + workspace membership.
- **Path parameter:** `workspace_id` (UUID).
- **200 OK:** an array of raw `files` rows (see
  [database.md](./database.md) for the columns).
- **Notes:** delegated to `db.get_files_by_workspace()` in `db.py` —
  that helper returns the Supabase `APIResponse` and the handler returns
  `.data` (or `[]` if `data` is falsy).

## `DELETE /workspaces/{workspace_id}/files/{file_id}`

Delete a file via the workspace-scoped path. Used by the editor's "Delete
File" button.

- **Auth:** required + workspace membership.
- **Path parameters:** `workspace_id`, `file_id` (both UUIDs).
- **200 OK:** `{ "message": "File deleted successfully" }`.
- **Side effects:** rows in `file_links` referencing this file are
  removed by `ON DELETE CASCADE`, not by the handler.

## `DELETE /files/{file_id}`

A second delete path that does **not** take the workspace in the URL.

- **Auth:** required + workspace membership (resolved via a lookup of the
  file's `workspace_id`).
- **Path parameter:** `file_id` (UUID).
- **200 OK:** `{ "message": "File deleted", "id": "<uuid>" }`.
- **404 Not Found:** when the file id does not exist.
- **Behavior difference from the workspace-scoped delete:** this handler
  *explicitly* deletes from `file_links` first (both as `source_file_id`
  and as `target_file_id`) before calling `db.delete_file()` on the row.
  The end-state is the same as the cascading delete, but the database
  work is done by the application instead of by the foreign-key
  constraint.

If you are wiring up a UI, prefer
`DELETE /workspaces/{workspace_id}/files/{file_id}` for symmetry with the
other file routes; both are exposed today.

## `PATCH /files/{file_id}/rename`

Rename a file.

- **Auth:** required + workspace membership.
- **Path parameter:** `file_id` (UUID).
- **Request body** (`FileRenameRequest`):
  ```json
  { "file_id": "<uuid>", "new_name": "renamed.txt" }
  ```
  The model declares `file_id` as a required field, but the handler uses
  the URL path parameter for the lookup and ignores `body.file_id`. Any
  string is accepted in that field; mismatched values do not error.
- **200 OK:** `{ "message": "File renamed", "new_name": "renamed.txt" }`.
- **404 Not Found:** when the file id does not exist.
- **Notes:** `file_links` rows store `source_file_name` and
  `target_file_name` for the file's old title; renaming the file does
  **not** rewrite those denormalized name columns. They will continue
  to reflect the previous title until the next save of the linking
  file rebuilds the row.
